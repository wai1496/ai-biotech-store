# AI BioTech Research Approval Workflow Design

## Purpose

Replace the current live-AI-first Research Insight behavior with a controlled publishing workflow where customers always read the latest admin-approved research stored in Supabase. AI is a research assistant only: it may fetch and draft, but it never publishes or overwrites approved content automatically.

## User-approved operating model

1. **Supabase is the source of truth for public research.**
2. **OpenAI is the primary on-demand research provider.**
3. **Gemini is an optional fallback provider.**
4. **Customers never trigger an AI request just by opening Research Insight.**
5. **Every AI refresh creates a new draft version.**
6. **The admin reviews the draft and source evidence before approval.**
7. **Only an explicit admin `Approve & Publish` action changes the public copy.**
8. **Previously published versions remain available for audit/rollback.**
9. **Raw provider/API errors are never exposed to customers.**
10. **Research content remains research-only: no individualized medical advice, dosing, administration, or treatment instructions are generated by this subsystem.**

## Existing system to preserve

The production database already has one `research_entries` row per published product (39 products / 39 entries) and public RLS permits reading rows where `published = true`. The current entries are placeholders with minimal content and empty references. The storefront product page already links to `/research-insight.html?product=<product_id>`.

`research_entries` therefore remains the stable **public/current published projection**. A new immutable version table holds drafts and publication history. This avoids breaking existing public reads while adding the approval layer.

## Data model

### Existing `research_entries` table — current public projection

Keep existing columns and add:

- `profile_json jsonb not null default '{}'::jsonb` — structured public profile used by Research Insight.
- `published_version_id uuid null` — points to the version that produced the public projection.
- `approved_by uuid null` — admin user who approved the current projection.
- `approved_at timestamptz null`.
- `published_at timestamptz null`.
- `verification_note text not null default ''` — optional admin note.

Existing `short_summary`, `full_content`, and `references_json` remain populated for backwards compatibility and generic Admin table views.

### New `research_entry_versions` table — draft/history store

Columns:

- `id uuid primary key default gen_random_uuid()`
- `research_entry_id uuid not null references research_entries(id) on delete cascade`
- `product_id text not null references products(id) on delete cascade`
- `version_number integer not null`
- `status text not null` with allowed values:
  - `draft`
  - `ai_reviewed`
  - `pending_admin_approval`
  - `published`
  - `rejected`
  - `superseded`
- `provider text not null default 'manual'`
- `model text not null default ''`
- `profile_json jsonb not null default '{}'::jsonb`
- `sources_json jsonb not null default '[]'::jsonb`
- `evidence_gate_json jsonb not null default '{}'::jsonb`
- `change_summary_json jsonb not null default '{}'::jsonb`
- `provider_metadata_json jsonb not null default '{}'::jsonb`
- `generated_at timestamptz null`
- `submitted_at timestamptz null`
- `approved_by uuid null`
- `approved_at timestamptz null`
- `published_at timestamptz null`
- `rejection_note text not null default ''`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Unique constraint: `(product_id, version_number)`.

RLS:

- Public/anonymous users receive **no access** to `research_entry_versions`.
- Authenticated admins with `super_admin` or `catalog_manager` may read/write versions.
- Public access remains limited to `research_entries where published = true`.

## Publishing transaction

Create an admin-only RPC `admin_publish_research_version(p_version_id uuid, p_verification_note text default '')`.

The RPC must run atomically and:

1. Verify caller is an active `super_admin` or `catalog_manager` using the existing `is_admin(...)` helper.
2. Lock the target version row.
3. Require target status to be `pending_admin_approval` or `ai_reviewed`.
4. Mark any prior `published` version for the same product as `superseded`.
5. Mark the target version `published`, set `approved_by`, `approved_at`, and `published_at`.
6. Copy its public fields to the existing `research_entries` row:
   - `short_summary = profile_json->>'short_description'`
   - `full_content = profile_json->>'overview'`
   - `references_json = sources_json`
   - `profile_json = profile_json`
   - `published = true`
   - `published_version_id = target version id`
   - approval metadata
7. Return the published version id and product id.

Create a second admin-only RPC `admin_reject_research_version(p_version_id uuid, p_reason text)` that marks a non-published version `rejected` and records the reason. It must never modify the public `research_entries` row.

## Research profile shape

Every AI/manual version uses the same structured object:

```json
{
  "short_description": "1–2 sentence neutral summary",
  "overview": "2–4 concise evidence-aware paragraphs",
  "molecular_identity": "Compound identity / class",
  "mechanism": "Targets and pathways",
  "research_areas": ["area one", "area two"],
  "evidence_context": "Human vs preclinical vs mechanistic evidence and uncertainty",
  "cautions": "Important limitations and formulation/equivalence caveats",
  "source_notes": "Short note describing source coverage"
}
```

No dose, administration schedule, diagnosis, treatment recommendation, individualized medical advice, or unsupported equivalence claim may appear in these fields.

## Evidence/source policy

The admin asked for a high-evidence research layer that still requires manual approval. The automated evidence gate therefore grades source quality but never publishes.

Preferred source domains for the first research pass:

- `pubmed.ncbi.nlm.nih.gov`
- `ncbi.nlm.nih.gov`
- `clinicaltrials.gov`
- `fda.gov`
- `ema.europa.eu`
- `who.int`

Each stored source object contains at least:

```json
{
  "title": "Source title",
  "url": "https://...",
  "domain": "pubmed.ncbi.nlm.nih.gov",
  "tier": "high",
  "supports": ["molecular_identity", "mechanism"],
  "retrieved_at": "ISO timestamp"
}
```

The evidence gate stores:

```json
{
  "passed": true,
  "high_quality_source_count": 3,
  "unique_domain_count": 2,
  "exact_product_evidence": "direct|component_only|limited|none",
  "human_evidence": "direct|indirect|none",
  "preclinical_evidence": "present|not_identified",
  "contradictions_found": false,
  "warnings": []
}
```

A draft can be generated even when the gate does not pass, but it must remain `draft` and the Admin UI must display the evidence warnings. A passing gate may move the draft to `pending_admin_approval`; it still cannot publish without the admin action.

For blends/stacks, component-level evidence must never be presented as proof of the exact combination. The draft must explicitly describe exact-combination evidence as limited/none when applicable.

## AI provider strategy and cost control

### Primary: OpenAI

Use the Responses API from a server-only Vercel function with:

- model: `OPENAI_RESEARCH_MODEL`, default `gpt-5.6-luna`
- web search enabled
- structured JSON output
- low reasoning effort / concise output
- `store: false`
- a bounded source/retrieval budget

OpenAI is only called when an authenticated admin presses **Fetch New Research** or **Refresh Research**. Customer page views never spend API tokens.

### Fallback: Gemini

If OpenAI is not configured or returns an upstream availability/quota error, the server may attempt the existing Gemini grounded search provider when `GEMINI_API_KEY` is configured.

Provider fallback must be visible to the admin in metadata (`provider`, `model`) but invisible as technical error detail to customers.

### No-provider behavior

Admin sees: `AI research is temporarily unavailable. Existing published research is unchanged.`

Customer sees the latest published Supabase copy with no provider warning unless there is no published research at all.

## Admin workflow

Replace the generic `Research Catalog` table experience with a focused Research workspace while preserving the existing admin navigation label.

Per product, show:

- current public version / published timestamp
- latest draft status
- provider/model
- evidence gate result
- number of high-quality sources
- `Fetch New Research`
- `Review Draft`
- `Approve & Publish`
- `Reject`
- `View Published`
- version history

### Fetch

1. Admin selects a product and presses `Fetch New Research`.
2. Browser sends the current Supabase access token to `/api/admin-research-refresh`.
3. Server verifies the user is an authorized admin.
4. Server calls OpenAI, optionally Gemini fallback.
5. Server returns structured profile, normalized sources, evidence gate, provider metadata, and a change summary compared with current published content.
6. Browser inserts a new `research_entry_versions` row through Supabase under the authenticated admin session.
7. Status is `pending_admin_approval` when evidence gate passes, otherwise `draft`.

### Review

The Review view displays **Published vs Draft** side by side (or stacked on mobile) with changed sections highlighted. Sources and evidence warnings are visible before the approval buttons.

### Approval

`Approve & Publish` invokes the transactional RPC. The approved version becomes immutable history. Editing afterwards means creating another draft/version, never modifying the published historical version directly.

### Manual draft

Admin may also create/edit a draft manually. Manual content follows the same versioning and approval process. AI is optional, not authoritative.

## Public Research Insight behavior

`research-insight.js` must stop calling `/api/ai-product-insight` during page load.

On load it queries:

- the selected published product
- its public `research_entries` row where `published = true`

It renders `profile_json` plus `references_json`. If structured fields are absent during migration, it falls back to existing `short_summary/full_content`.

Public states:

- **Published profile available:** render it immediately.
- **No approved profile:** show `Research profile is being prepared. Please check again later.`
- **Supabase/network failure:** show a neutral temporary-unavailable message; do not mention OpenAI, Gemini, API keys, quotas, Vercel, database internals, or raw errors.

## Research Catalog relationship

Research Catalog is the browse/index layer. Research Insight is the deeper detail layer for the same product.

Research Catalog cards should use the approved `research_entries.short_summary` where available and continue to link to the corresponding Research Insight detail page. AI-generated drafts never appear in the catalog before approval.

## Authentication/security

- OpenAI and Gemini keys remain Vercel server environment secrets only.
- Browser code never receives provider keys.
- `/api/admin-research-refresh` requires a valid Supabase bearer token and an active admin role.
- Draft/history table is protected by RLS from anonymous reads.
- Publication happens only through the admin RPC, not a public table update.

## Migration/backfill

The existing 39 placeholder `research_entries` rows remain published during rollout so product links do not break.

Do **not** automatically treat the placeholder text as scientifically approved content. After the new workflow is live, the admin can refresh and approve products progressively. The public detail page may identify a placeholder entry as `Research profile is being prepared` until a real published version exists.

No product, variant, inventory, order, wallet, protocol, or customer data is changed by this research migration.

## Failure handling

- OpenAI quota/upstream failure → optional Gemini attempt.
- Gemini quota/upstream failure → admin fetch fails safely; published copy stays unchanged.
- Evidence gate fails → save draft with warnings; approval remains possible only after manual review, but no automatic status promotion.
- DB insert fails → show admin error; no published content changes.
- Publish RPC fails → transaction rolls back; previous public version remains intact.
- Customer DB read fails → neutral temporary message.

## Testing and release gates

Before production promotion:

1. Database migration applies successfully with RLS enabled.
2. Anonymous user can read published `research_entries` but cannot read `research_entry_versions`.
3. Non-admin authenticated user cannot create/publish research versions.
4. Admin can create a draft and see its evidence metadata.
5. `Approve & Publish` atomically updates the public projection and marks the old version superseded.
6. Rejecting a draft leaves the public copy unchanged.
7. Research Insight makes **zero AI requests** on customer page load.
8. Customer Research Insight continues to render when both AI providers are unavailable.
9. Raw provider errors/API key names never appear in customer HTML.
10. Mobile and desktop Admin Review layouts remain usable.
11. Existing storefront, cart, checkout, catalog, product, member, and protocol smoke checks continue to pass.

## Out of scope for this feature

- Automated publishing without admin approval.
- General-purpose customer chatbot.
- Protocol dosing or administration generation.
- Personalized medical advice or treatment recommendations.
- Automatic modification of product/variant/inventory data.
- Progress Control Center promotion and Peptide Calculator navigation fixes; those remain separate workstreams.
