## Supabase rollback rules

### Before every data/schema change

Capture:

- Target project ID.
- Exact SQL/migration name.
- Affected tables and row counts.
- Primary keys and before-state values for changed rows.
- Current migration list.
- Storage object paths/metadata for changed assets.
- The reversal SQL or restoration source.

### Data-change rollback

For update/insert/delete operations:

1. Use a change batch or snapshot table where the staging schema provides it.
2. Store before-state JSON keyed by table and primary key.
3. Apply the smallest scoped change.
4. Validate after-state counts and business invariants.
5. On failure, restore the captured rows and rerun validation.

Never use broad destructive SQL such as unscoped `DELETE`, `TRUNCATE`, mass reseed or schema reset.

### Migration rollback

1. Do not merge Supabase development branches or migrations into another project without explicit approval.
2. Every new migration must document its reverse operation.
3. Prefer additive schema changes before destructive changes.
4. For a failed additive migration, apply a separately named corrective migration; do not rewrite recorded migration history.
5. For destructive changes, require a verified export/snapshot and explicit owner approval.

### Media/master rollback

For `media_templates` or Storage changes:

1. Preserve the previous URL, version, hash/path and label configuration.
2. Upload a new version rather than overwriting the existing object.
3. Switch the active record only after validation.
4. Roll back by restoring the previous `master_image_url`, version and configuration.
5. Do not delete previous master objects until the release is locked and retention is approved.

## Environment-split emergency rule

Current code uses both Supabase projects. If a test reveals a write went to the wrong project:

1. Stop the related workflow immediately.
2. Record the request, user, timestamp, table and row IDs.
3. Disable the offending route/config in the review branch.
4. Compare the affected row with the baseline.
5. Restore only the unintended staging/test rows; do not alter legitimate operational rows.
6. Add a regression test proving the route uses the intended environment.
